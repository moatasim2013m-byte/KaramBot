# Capital Bank / CyberSource Secure Acceptance Root Cause Investigation

## Context
The user-facing error page (`secureacceptance.cybersource.com`) shows:

- **"You are not authorized to view this page. The transaction has not been processed."**
- Error reference similar to: `E-...`

This error is generated by CyberSource/Capital Bank **before payment authorization**, which usually indicates a **Hosted Checkout request/configuration mismatch** rather than a card decline.

---

## Most likely root causes from current implementation

### 1) Environment/Profile/Endpoint mismatch (highest probability)
The backend validates env/host/path consistency and can reject if values do not match (`test` vs `prod`, host/path mismatch), which aligns with CyberSource "not authorized" failures when profile credentials belong to a different environment.

Code paths:
- `CAPITAL_BANK_ENV` normalization and endpoint resolution. 
- Validation requiring environment host alignment and `/pay` path.

If bank provisioned **test profile** while app posts to **live host** (or vice versa), CyberSource can render the unauthorized page.

### 2) Merchant/Profile/Access key tuple not belonging to same account
Secure Acceptance requires a valid linked tuple:

- `merchant_id`
- `profile_id`
- `access_key`
- signature generated with matching `secret_key`

Any cross-account or stale value typically triggers hosted page authorization failure.

### 3) Signature mismatch due to secret key encoding assumptions
Signature is HMAC SHA-256 with key decoding mode (`auto` / `base64` / `hex` / `utf8`).
If secret key format is misinterpreted by auto-detection, generated signature may be invalid even though values "look" correct.

### 4) Unregistered return/cancel domain in Secure Acceptance profile
The request uses dynamic origin-driven return URLs:

- `override_custom_receipt_page = <origin>/api/payments/capital-bank/return`
- `override_custom_cancel_page = <origin>/payment/cancel`

If `origin` resolves to a domain not whitelisted in the bank/CyberSource profile, hosted checkout can deny request.

### 5) Field-policy mismatch in bank profile
The app signs a fixed required field set including billing fields and locale. If the profile's hosted checkout rules differ (required/forbidden field policy), request can be rejected upstream.

---

## Evidence collected from code

### Secure Acceptance request generation
- Builds signed fields including `access_key`, `profile_id`, `transaction_uuid`, `amount`, `currency`, billing fields.
- Posts to CyberSource hosted checkout endpoint `/pay`.

### Preflight validation already exists
- Validates required env vars and endpoint host/path compatibility.
- Validates payload has required signed fields and signature inputs.

### Frontend flow
- Checkout page calls `/api/payments/capital-bank/initiate`.
- Creates POST form and submits to returned CyberSource URL with backend-signed fields.

So the architecture is correct; likely failure is in **credential/environment/domain registration consistency**.

## Immediate investigation checklist (bank-facing)

1. **Capture one failing attempt server log bundle** (same timestamp as screenshot error reference).
   - from `/capital-bank/initiate`: endpoint, env, profile id preview, reference number, transaction UUID.
2. **Confirm environment pairing with bank**:
   - If profile is test, endpoint must be `https://testsecureacceptance.cybersource.com/pay`.
   - If profile is prod, endpoint must be `https://secureacceptance.cybersource.com/pay`.
3. **Ask bank/CyberSource support to verify this exact tuple**:
   - merchant ID
   - profile ID
   - access key
   - secure acceptance key/secret
4. **Confirm allowed origins/return URLs in profile**:
   - production site origin
   - any www/non-www variants
   - no staging domain accidentally sent in production
5. **Verify secret key encoding mode**:
   - explicitly set `CAPITAL_BANK_SECRET_KEY_ENCODING` to bank-confirmed format; avoid `auto` during incident triage.
6. **Use the screenshot Error Reference Number** (`E-...`) with bank to fetch CyberSource-side rejection reason.

## Suggested remediation order

1. Lock env to correct target (`test` or `prod`) and matching endpoint.
2. Reissue/rotate bank credentials as a complete set (merchant/profile/access/secret together).
3. Force explicit `CAPITAL_BANK_SECRET_KEY_ENCODING` based on bank guidance.
4. Register all real checkout origins and return URLs in Secure Acceptance profile.
5. Re-run end-to-end checkout and compare new attempt with bank-side logs using reference number.

---

## Conclusion
Given current code behavior, the strongest root-cause hypothesis is **bank-side credential/profile/environment authorization mismatch** (including allowed return URL/domain mismatch), not business logic amount calculation or transaction finalization code.
