1. **Blocker — `backend/src/services/messageProcessor.js`: `persistInbound`, `claimInbound`, `countInbound`, `needsProcessing` — persistence is not atomic or crash-idempotent.**  
   **Scenario:** Delivery A changes a message from `persisting` to `received`/`delivered`, then dies before updating conversation counters. Delivery B sees the already-claimed row, skips counting and processing, and returns 200. Thus 200 does not guarantee persisted counters. For external/restaurant/clinic tenants, a crash after claiming but before post-response processing also permanently loses the forward/reply: retries skip it, and the SHIFT sweeper cannot recover it. An uncertain result from the unread increment can additionally cause a second increment on retry.  
   **Fix:** Commit message insertion/claim and conversation counters in one short Prisma transaction. Separately retain a durable *processing-pending* marker, using existing JSON fields if necessary, until forwarding/workflow processing completes. Recover that queue after restart; persistence ownership must not mean processing completed. PgBouncer transaction mode supports these transactions.

2. **Blocker — `backend/src/services/replyBatcher.js`: `runLeased`, `deliver`, `sendPart`; `backend/src/db/jsonb.js`: `renewLease` — expired workers can still write and send.**  
   **Scenario:** A renews its lease and reads existing outbounds, then stalls during subsequent DB work for over 60 seconds. B acquires the expired lease and sends. A resumes, creates another intent and sends using its old duplicate-check result. There is no further ownership check before Graph. Renewals inside `runLeased` also ignore `false`; state writes and commits are unfenced. `renewLease` accepts an already-expired token when nobody has replaced it yet.  
   **Fix:** Require an unexpired matching token for renewal and abort on every failed renewal. Fence state/intent mutations with token and expiry predicates in short transactions. Recheck ownership before each Graph attempt and enforce an overall bounded send duration. Do not infer that another worker’s send is dead merely because its lease expired. External-send ambiguity still requires the handling in finding 3.

3. **Blocker — `backend/src/services/replyBatcher.js`: `deliver`, `recoverCovered`; `backend/src/services/shiftSweeper.js`: `sweepAmbiguous` — an unsent intent becomes an answered customer message.**  
   **Scenario:** The process creates `sending`, then crashes **before calling Graph**. Recovery treats that intent as covering the batch, marks inbound rows `answered`, and never retries. The customer receives nothing. The later ambiguous alert is optional and best-effort; there may be no configured channel. A timeout has the same terminal treatment even when nothing arrived.  
   **Fix:** Keep uncertain sends unresolved and their inbound rows visibly awaiting resolution, rather than marking them answered. Provide a durable Inbox work item and a resolution/reconciliation workflow. Explicitly obtain an owner decision about the unavoidable tradeoff: with no Graph idempotency mechanism, both “never duplicate” and “always eventually deliver exactly one reply” cannot be guaranteed after an unknown send outcome. Do not ship this implementation as satisfying both.

4. **Major — `backend/src/services/whatsapp.js`: `classifySendError`; `backend/src/services/replyBatcher.js`: `sendPart` — generic HTTP 5xx responses trigger unsafe POST retries.**  
   **Scenario:** Graph accepts a message, but an intermediary returns 502 while returning the response. The code classifies every 5xx as safely retryable and immediately POSTs the same message again. Both can reach the customer.  
   **Fix:** Retry only failures known to precede acceptance, or documented Graph rejection codes that guarantee no send occurred. Treat generic gateway/server errors with unknown acceptance as ambiguous and use the unresolved-send workflow.

5. **Major — `backend/src/services/messageProcessor.js`: `processShiftItem`; `backend/src/services/replyBatcher.js`: `runLeased` — opt-out processing is neither durable nor serialized.**  
   **Scenario:** For `STOP`, queued rows are marked `skipped` before the opt-out state or acknowledgement intent is persisted. A crash or state-write failure there loses the acknowledgement and leaves marketing opt-out unset; retries skip the claimed message and the sweeper ignores skipped rows. Conversely, if the instance dies before `processShiftItem`, the sweeper sends the still-`received` STOP through ordinary AI processing instead of deterministic opt-out handling. Reactions have the same bypass of preprocessing. The direct opt-out delivery also runs without the conversation lease.  
   **Fix:** Move deterministic command/type handling into the durable leased worker. Commit opt-out state, cancellation of queued sales work, and durable acknowledgement intent atomically. Do not terminally skip the command before its required work is recoverable.

6. **Major — `backend/src/routes/inbox.js`: `/send`, `/claim`; `backend/src/services/replyBatcher.js`: `deliver`, `answerTaps`; `backend/src/services/shiftSweeper.js`: note delivery — staff activity does not serialize with bot sends.**  
   **Scenario:** The batcher passes its final staff check. Staff then claim the conversation and receive an acknowledgement; the batcher continues writing state and sends its old sales reply afterward. The conditional state update may affect zero rows, but `deliver` ignores that and still sends. `/send` installs the pause only after the staff Graph send. Sweeper notes likewise use stale conversation snapshots and no reply lease.  
   **Fix:** Persist staff pause/claim intent **before** staff sending, through the same per-conversation dispatch coordination as bot output. Revalidate human state at dispatch, abort on rejected conditional transitions, and serialize notes and button replies too. Distinguish already-dispatched messages from cancellable work.

7. **Major — `backend/src/services/messageProcessor.js`: `handleStatuses` — definitive asynchronous delivery failures leave inbound rows answered.**  
   **Scenario:** Graph returns a wamid, so the batcher marks the batch answered. Meta subsequently reports `failed`, for example a temporary delivery failure. `handleStatuses` only changes the outbound status, with an extra alert for billing errors. No inbound is requeued and no general failure work item is created. Recovery only collects `received`, so the customer remains unanswered.  
   **Fix:** On a definitive failed covering outbound, inspect its `batch_ids`; if no other successful or unresolved covering send exists, atomically requeue eligible inbound rows or park them for explicit staff resolution. Apply reason-aware retry limits and alert on terminal failures.

8. **Major — `backend/src/services/messageProcessor.js`: `mayReconcile`, `handleStatuses` — recipient/time proximity is not message correlation.**  
   **Scenario:** An ambiguous bot send exists. Staff claim the chat and send a claim acknowledgement. Its delivery webhook arrives before `/claim` creates the message row. There is no newer outbound intent for that send, so the webhook attaches the claim acknowledgement’s wamid to the unrelated ambiguous bot message. The actual claim row then encounters the unique-wamid conflict, and the unsent bot reply can falsely appear delivered.  
   **Fix:** Supply a persisted unique intent identifier through WhatsApp’s supported `biz_opaque_callback_data` and reconcile using the echoed identifier. Otherwise, leave unmatched statuses unmatched; do not guess identity from recipient and timestamps. Include claim acknowledgements and notes in the intent protocol.

9. **Major — `backend/src/services/replyBatcher.js`: `scheduleReply`, `runLeased` — instance-local debounce and fallback freshness produce multiple replies to one burst.**  
   **Scenario:** A question on instance A schedules a short timer. Further fragments arrive on B before and just after A starts generation; B’s timer cannot extend A’s timer and subsequently loses the lease. If A’s AI fails, freshness explicitly excludes fallback results, so A sends a fallback covering only its original batch. Rescheduling processes the remaining fragment and can send a second fallback. Successful generation also sends stale content when another fragment arrives during the one permitted text regeneration.  
   **Fix:** Persist the conversation’s quiet deadline/batch generation so all instances honor the same debounce. Validate batch generation at dispatch. For a generic failure acknowledgement, include all eligible fragments accumulated for that burst instead of scheduling another fallback for them.

10. **Major — `backend/src/services/shiftSweeper.js`: `sweepOrphans`, `sweepAwaitingNotes` — a temporary staff pause permanently strands messages.**  
    **Scenario:** Staff send at 10:00 without taking over. A customer asks another question at 10:05; the batcher parks it as `awaiting_staff`. Nobody replies. At 10:30 the pause expires, but no worker restores the message to `received`. The awaiting sweep only sends a waiting note; it never resumes answering. For “price please”, `isCloser` suppresses even that note because it treats every question-mark-free message of three words or fewer as a closer.  
    **Fix:** Requeue unresolved awaiting rows when temporary human activity expires, unless explicit takeover/AI-disable still applies. Recognize actual closing phrases rather than using word count alone.

11. **Major — `backend/src/services/shiftSweeper.js`: `sweepSlaNotes`, `sweepAwaitingNotes` — permanent claims can consume work that never happened.**  
    **Scenario:** A sweep writes `sla_note_sent_at` or `awaiting_note_for`, then crashes before creating the outbound intent or alerting staff. Subsequent sweeps regard the work as completed forever. Additionally, an SLA request can be replaced between reading it and `claimFlag`; the old sweep then marks the **new** request’s note as sent while acting on the old request.  
    **Fix:** Atomically create a durable note/alert intent tied to the specific request identity. Use claimed/in-progress versus completed states, with reclaimable ownership, and compare the request’s `at`/reason when claiming. Resume pending work after restart; apply ambiguity handling only once dispatch may have happened.

12. **Major — `backend/src/workflows/shift/results.js`: `captureResult`; `backend/src/services/replyBatcher.js`: `deliver` — “time noted” can contradict persisted lead data.**  
    **Scenario:** An open high-priority `person` request exists, and staff have set `preferred_time` to 10:00. The customer requests 17:00. `captureResult` builds an acknowledgement saying 17:00 was noted, but lead merging refuses to overwrite the staff-owned field, and the higher-priority team request prevents recording a new meeting entry. `deliver` also proceeds when `saveLead` returns `ok:false` after version conflicts.  
    **Fix:** Build factual acknowledgements from the successfully persisted result, not a pre-write proposal. Treat failed/conflicting saves as a failed state transition. If staff-owned time cannot change, durably record a separate requested change and acknowledge that accurately.

13. **Major — `backend/src/routes/inbox.js`: `PATCH /conversations/:id/lead` — resolving one request can hide a newer request.**  
    **Scenario:** The route successfully sets the old request’s `resolved_at`. Before its separate status update, the bot writes a new unresolved request and sets `pending`. The route then changes that conversation to `open` because it checks only status. The new request disappears from the needs-team filter and SLA sweep.  
    **Fix:** Resolve the matching request and change conversation status in one transaction/conditional statement, verifying that the stored request is still the same resolved entry. Apply the same atomicity principle to creating/replacing requests and their pending status.

14. **Major — `frontend/src/pages/InboxPage.jsx`: `LeadCard`, `LeadFieldRow` — an editing draft survives switching customers.**  
    **Scenario:** Staff start editing customer A’s preferred time, then open customer B without closing the editor. React reuses `LeadCard` and field rows because they are not keyed by conversation. The draft remains A’s, but `onSave` now targets B’s conversation and version. Clicking Save writes A’s information into B’s lead.  
    **Fix:** Key `LeadCard` by `selected.id`, or reset all editor state on conversation changes. Bind saves to the conversation/version where editing started.
